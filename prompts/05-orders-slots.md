# 05 · Слоты, заказы, статусы, staff (backend)

Режим: сначала Plan, после OK — Build. Это самая рискованная фаза: план должен явно описать, как ты избегаешь гонок при резервировании.
Прочитай `AGENTS.md`, `docs/SPEC.md` полностью (особенно 5.4–5.8 и раздел 6).

## Цель
Заказ создаётся надёжно, слот не переполняется, статусы меняются по правилам, бариста получает события в реальном времени.

## Что сделать
1. **Модели и миграции:** Order, OrderItem (снапшоты), SlotLoad, OrderStatusEvent. Счётчик кода заказа по точке за локальный день (`TV-042`), без дыр и гонок.
2. **SlotService:**
   - `list_slots(location, units, now)`: слоты на сегодня по правилам 5.4, с полями `start`, `available`, `remaining`, плюс `asap` (первый доступный слот).
   - `reserve(...)` и `release(...)` в транзакции с блокировкой.
3. **OrderService.create:** проверить идемпотентность → провалидировать и пересчитать цену (переиспользуй `SelectionValidator` и `PriceCalculator` из фазы 02) → проверить рабочие часы и слот → зарезервировать → сохранить заказ со снапшотами и `access_token` → записать событие → опубликовать в шину. Статус сразу `confirmed`. `is_asap=true` назначает первый доступный слот.
4. **Статусная машина:** переходы и права из SPEC 5.5. Отмена освобождает слот. Каждый переход пишет `OrderStatusEvent`.
5. **EventBus:** `Protocol` + реализация в памяти (asyncio-очереди по каналам `order:{id}` и `location:{id}`). Готовь интерфейс так, чтобы Redis можно было подставить без правок сервисов.
6. **Эндпоинты клиента:** `GET /locations/{id}/slots`, `POST /orders`, `GET /orders/{id}`, `GET /orders/{id}/events` (SSE, keepalive, токен), `POST /orders/{id}/cancel`.
7. **Staff:** `POST /staff/login` (PIN → токен точки, ограничение попыток), `GET /staff/orders`, `GET /staff/orders/stream` (SSE), `POST /staff/orders/{id}/status`, `GET /staff/availability`, `PUT /staff/availability/products/{id}`, `PUT /staff/availability/options/{id}`. Все проверяют, что заказ и позиции принадлежат точке из токена. PIN'ы демо-точек в seed и в `.env.example` (только для dev).
8. `make gen-api`, клиент обновлён.

## Тесты (обязательны)
- **Гонка:** N параллельных `POST /orders` на слот с вместимостью M: успешных ровно столько, сколько вмещается, остальные получают `slot_unavailable`. Тест реально параллельный, на настоящей БД.
- Идемпотентность: повтор с тем же ключом и телом даёт тот же заказ и не удваивает резерв; другое тело — `idempotency_conflict`.
- Слоты: `lead_time`, округление до шага, границы часов работы, закрытая точка, `order_too_large`.
- Статусы: все разрешённые и запрещённые переходы, права `customer` и `staff`, отмена освобождает вместимость.
- Цена в заказе пересчитывается на сервере (клиент не может подсунуть цену).
- Стоп-лист: заказ с недоступной позицией отклоняется.
- Доступ: чужой токен, чужая точка, отсутствие токена.
- SSE: подписчик получает событие о смене статуса.

## Границы (не делай)
Онлайн-оплату, аккаунты клиентов, UI, Redis, уведомления. Не меняй правила SPEC: если видишь проблему, остановись и опиши её.

## Критерии готовности
`make test` и `make lint` зелёные, тест гонки стабилен (прогони 20 раз); сценарий из `curl`: слоты → заказ → статус → SSE → смена статуса стаффом — работает; в отчёте таблица «правило SPEC → тест, который его проверяет».
