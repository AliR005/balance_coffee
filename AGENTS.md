# Balance — приложение для заказа кофе

Заказ кофе в кофейнях «balance»: выбор точки, состава напитка и времени готовности.
Сейчас строим демо-MVP для презентации клиенту, но пишем код как основу продукта.

## Источники правды (читай перед каждой задачей)
- `docs/SPEC.md` — что делаем, бизнес-правила, API
- `docs/DESIGN.md` + `design/tokens.css` — как выглядит и двигается
- `prompts/` — фазы работы; текущая фаза указана в задаче
- `docs/BACKLOG.md` — сюда одной строкой записывай идеи «на потом», вместо того чтобы делать их сейчас

Если задача противоречит SPEC или DESIGN — остановись и спроси. Не выбирай молча.

## Стек
- `backend/`: Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, Pydantic v2, PostgreSQL 16, pytest (+pytest-asyncio), ruff, mypy, uv
- `web/`: React + TypeScript (strict) + Vite, Tailwind CSS v4, shadcn/ui (только как основа на Radix, стилизуется под токены), Framer Motion, TanStack Query, Zustand, React Router, vitest, Playwright
- API-клиент для фронта генерируется из OpenAPI (orval). Типы API руками не писать.
- Docker Compose: `db`, `api`, `web`. Прод: Caddy + docker-compose.prod.yml.

## Архитектурные правила
- Модульный монолит. router — только HTTP; логика — в service; SQL — только в repository.
- Модули общаются через функции service, а не лезут в чужие модели и таблицы.
- Деньги — `int` в минимальных единицах валюты. Никогда `float`.
- Цену заказа считает только сервер. Клиент показывает предпросчёт той же логикой.
- Заказ хранит снапшот: названия, опции, цены на момент заказа. Изменение меню не меняет историю.
- Внешнее (оплата, уведомления, шина событий) — за интерфейсами (`Protocol`), реализация подменяема.
- `location_id` учитывается везде, где важны наличие, часы работы и нагрузка.
- Время хранится в UTC, показывается в часовом поясе точки.
- Ошибки API — единый формат `{code, message, details}`, коды перечислены в SPEC.
- Создание заказа идемпотентно (`Idempotency-Key`). Резервирование слота — в транзакции с блокировкой.

## Фронтенд-правила
- Тема по умолчанию тёмная (часть бренда), светлая запасная. Название в интерфейсе одно: «balance».
- Дизайн фото-центричный: у продукта есть `image_url`; пока фото нет, используется заглушка (`Photo` → пресет или `DrinkCup`).
- Эталон вида и поведения — `design/preview.html`; сверяйся с ним, а не с внешними референсами.
- Никаких хардкод-цветов, радиусов, теней и шрифтов в компонентах — только токены из `tokens.css`.
- Mobile-first: 390px — основной размер. Проверяй и 360px, и планшет 1024px (экран баристы).
- Интерфейс тёмный (светлая «сливочная» панель только на оформлении), светлой темы в MVP нет.
- Движение — по DESIGN.md: самопроизвольно движутся только ролики и стакан на hero и старте. Ролики играют лишь когда видны. Уважай `prefers-reduced-motion`.
- Любое состояние данных имеет вид: загрузка (скелетон), пусто, ошибка (с действием), успех.
- Доступность: фокус виден, все интерактивные элементы доступны с клавиатуры, у иконок есть `aria-label`.
- Тексты интерфейса — на русском, через словарь `web/src/shared/i18n` (не строками в компонентах).

## Как ты работаешь
1. Сначала краткий план (файлы, шаги, риски) — жди подтверждения.
2. Малые шаги. После каждого — `make lint` и `make test` зелёные.
3. Делай только то, что есть в текущей фазе. Остальное — в `docs/BACKLOG.md`.
4. Новая зависимость — только с объяснением, зачем и чем не подошло имеющееся.
5. Миграции — только через Alembic; применённые миграции не редактируй.
6. Логика цены, слотов, статусов и валидации опций — только вместе с тестами.
7. Не коммить сам. В конце предложи текст коммита.
8. Итог фазы — отчёт: что сделано; как проверить (точные команды); что отклонилось от плана; открытые вопросы.
